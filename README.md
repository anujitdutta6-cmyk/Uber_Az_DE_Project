## 1. Project overview

A ride-booking platform produces two broad categories of data:

1. **Historical and reference data** — bulk ride records and mapping datasets used to interpret payment methods, cancellation reasons, ride types, ride statuses, vehicle makes and vehicle types.
2. **Live ride events** — booking and ride lifecycle events generated by an application and sent through Azure Event Hubs.

The intended Azure architecture combines **Azure Data Factory (ADF)** for batch ingestion and orchestration with **Azure Databricks, PySpark and Spark Structured Streaming** for distributed processing. Delta Lake provides reliable table storage, while declarative pipeline definitions organise repeatable transformations and downstream dependencies.

The analytical output is a **Star Schema** with one ride-level fact table and dimensions for drivers, payments, vehicles, locations, passengers and bookings.

### What this project demonstrates

- Batch and event-driven ingestion in one platform.
- Bronze / Silver / Gold Medallion Architecture.
- PySpark data cleansing, standardisation, deduplication, joins and validation.
- Incremental processing and CDC-style change application.
- SCD Type 1 for current-state attributes and SCD Type 2 where history matters.
- Declarative transformation flows, dependency management and table quality checks.
- Production-minded recovery, replay, monitoring and environment separation.

### Layer responsibilities

- **Sources:** ride events, historical ride datasets and mapping/reference data.
- **Event Hubs:** buffers event messages and decouples producers from consumers.
- **ADF:** orchestrates scheduled or parameterised batch ingestion and dependencies.
- **Bronze:** preserves source-shaped records and ingestion metadata for audit and replay.
- **Silver:** standardises schemas, cleans records, deduplicates, validates and joins reference data.
- **Silver OBT:** central enriched ride-level dataset that simplifies dimensional modelling.
- **Gold:** fact and dimension tables designed for analytics.
- **Databricks / Spark:** executes distributed batch and streaming transformations.
- **Monitoring:** captures pipeline status, stream progress, data quality outcomes and alerts.

## 4. End-to-end data flow

### Path A — historical / batch

1. ADF starts a pipeline manually, on a schedule, or through a dependency.
2. Copy activities ingest historical ride files and mapping datasets into ADLS Gen2.
3. ADF passes configuration such as source path, destination path, file format and load date through parameters.
4. Databricks reads Bronze data using explicit schemas where possible.
5. PySpark validates types, normalises fields, handles nulls and duplicates, and applies business rules.
6. Clean ride records and mapping data become Silver inputs.
7. The Silver OBT combines rides with applicable reference data.
8. Downstream pipeline flows create or refresh fact and dimension outputs.
9. Reconciliation compares source counts, accepted/rejected rows and target counts.

### Path B — real-time ride events

1. A booking/event producer serialises a ride event, commonly as JSON.
2. The producer sends the event to an Azure Event Hubs entity.
3. Databricks consumes the stream using Spark Structured Streaming and an explicit event schema.
4. The stream parses the payload, extracts event time and identifiers, validates required fields and adds ingestion metadata.
5. Valid events are persisted to a Bronze Delta target; malformed messages are recorded or quarantined.
6. Silver processing standardises events and handles duplicates/replays using a stable event or ride key and appropriate sequence logic.
7. Enriched records become available to the Silver OBT and downstream transformation flow.
8. Declarative pipeline flows update curated tables according to their configured processing mode and dependencies.
9. Monitoring tracks stream progress, latency, input rates, errors and checkpoint health.

**Why separate batch and streaming at ingestion?** Batch is effective for historical backfills and reference data; streaming supports newly arriving ride events. Both paths should converge on consistent Silver contracts so Gold has one definition of business logic.

### Complete downstream flow after Silver OBT

The OBT should provide a consistent business-level ride record. Downstream views project it into targets with the correct grain.

1. **Driver dimension:** select driver attributes, standardise the business key, resolve duplicates and apply the selected SCD policy.
2. **Payment dimension:** standardise payment method identifiers and labels; use a controlled unknown member for unmatched valid rides.
3. **Fact view:** select measures and dimension business keys; enforce one row per agreed ride/fact grain; resolve dimension surrogate keys before writing the fact.
4. **Vehicle dimension:** consolidate vehicle attributes and mapping values, including vehicle type and make where available.
5. **Location dimension:** standardise pickup/drop-off location attributes. If historical location classification matters, use Type 2 tracking or a separate history model.
6. **Passenger dimension:** resolve passenger identifiers and only the descriptive attributes approved for analytics.
7. **Booking dimension:** represent booking-specific descriptive attributes that are not measures of the ride itself.

The exact columns and keys must be confirmed from the actual source schemas and transformation code. Node names are not a complete column-level contract.

## 6. Data layers and definitions

| Layer / object | Purpose | Typical contents | Main quality rules |
|---|---|---|---|
| Bronze — raw rides | Preserve bulk ride input | Source columns, source file/path, ingestion time, batch/run ID | File readability, source schema, record counts |
| Bronze — raw events | Preserve event payloads | Payload, event ID/time, ingestion time, available Event Hubs metadata | Parse status, event ID presence, replay traceability |
| Silver — staging rides | Consistent ride structure | Typed IDs, timestamps, statuses, amounts and cleaned fields | Required fields, valid ranges, duplicate policy |
| Silver — mapping inputs | Standardise reference data | Payment, cancellation, status, ride and vehicle mappings | Unique mapping key, non-null descriptions, unmatched-code report |
| Silver — silver_obt | Enriched business-level records | Ride fields plus mapped descriptions | Join cardinality, key coverage, expected grain |
| Gold — dimensions | Reusable descriptive entities | Driver, payment, vehicle, location, passenger, booking | Key uniqueness, SCD rules, current-row consistency |
| Gold — fact | Ride measures and dimension keys | Ride-level measures, foreign keys and audit attributes | Fact grain, valid measures, FK coverage |

### Recommended Bronze metadata

Where feasible, retain:

- **_ingested_at** — when the platform received the record.
- **_source_file / source entity** — origin of the record.
- **_run_id / batch ID** — pipeline execution identity.
- **_event_time** — business event time, distinct from ingestion time.
- **_record_hash** — optional hash for change detection or reconciliation.
- **parse status / rescued data** — unexpected fields or malformed values, where supported.

Avoid overwriting raw history just to make a downstream transformation pass. Correct the transformation and replay from a known boundary where practical.

### Fact table — fact

**Recommended grain:** one row per unique ride/booking fact event, as confirmed by business rules and source keys. If one ride can emit multiple lifecycle events, decide whether the fact represents the latest ride state, one row per ride, or one row per event. Do not mix these grains.

| Attribute group | Example fields (illustrative) | Purpose |
|---|---|---|
| Business identifiers | ride_id, booking_id | Trace the fact to source |
| Dimension foreign keys | driver_key, payment_key, vehicle_key, location_key, passenger_key, booking_key | Enable star-schema joins |
| Measures | fare, distance, duration, tip or other available metrics | Support aggregation and KPIs |
| Status attributes | ride status, cancellation code where appropriate | Support operational analysis |
| Audit attributes | event time, ingestion time, run ID | Reconciliation and freshness monitoring |

These are proposed column groups, not a claim that every field already exists in the notebooks. Match the final schema to actual source data.

### Dimension definitions

| Table | Business purpose | Candidate business key | Example attributes | History policy to consider |
|---|---|---|---|---|
| dim_driver | Driver profile | driver_id | approved profile attributes, status | Type 1 or Type 2 based on reporting needs |
| dim_payment | Payment classification | payment method ID/code | method name, category | Usually Type 1 |
| dim_vehicle | Vehicle characteristics | vehicle_id | vehicle type, make, descriptions | Type 2 if historical attributes matter |
| dim_location | Location reference | location ID or natural key | location code/name/zone | Type 2 if historical classification matters |
| dim_passenger | Passenger entity | passenger_id | approved, minimised descriptive fields | Depends on need and privacy policy |
| dim_booking | Booking context | booking_id | booking channel/type and other available descriptors | Type 1 unless history is required |

**Key design rules**

- Use a stable business key to identify the real-world entity.
- Use a warehouse-managed surrogate key when the model needs stable identity and Type 2 versions.
- A Type 2 dimension may contain multiple rows per business key; the fact must resolve the version valid at ride event time.
- Use an explicit unknown/default dimension member when a valid fact arrives before its dimension record, and measure how often it happens.
- Avoid sensitive passenger attributes unless there is a documented, authorised business need.

## 8. Batch and real-time processing

### Batch — ADF + Databricks

Use ADF for historical loads, reference-data refreshes, dependency management and controlled backfills. Parameterise source/sink paths and load dates rather than hard-coding a pipeline for every file. Databricks performs distributed transformations and writes Delta targets.

**Typical sequence:** trigger → validate configuration → copy/land source → run notebook or pipeline → validate output → record metrics → publish success status.

### Real-time — Event Hubs + Structured Streaming

Use Event Hubs as the event buffer and Structured Streaming as the incremental processing engine. Parse a known schema, apply event-time logic where needed, and write to a durable Delta target.

Illustrative PySpark pattern; configuration and authentication are intentionally omitted:

~~~python
from pyspark.sql.functions import col, from_json

# event_schema must match the producer's contract.
raw_events = (
    spark.readStream
    .format("eventhubs")
    .options(**event_hub_options)
    .load()
)

parsed_events = (
    raw_events
    .select(from_json(col("body").cast("string"), event_schema).alias("event"))
    .select("event.*")
)

query = (
    parsed_events.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", checkpoint_path)
    .toTable("catalog.bronze.ride_events")
)
~~~

This is a pattern, not drop-in runnable code. Connector options, schema, table names and checkpoint storage must be configured for the workspace. Never commit connection strings or secrets.

### Streaming correctness checklist

- Use a durable checkpoint location per query and environment.
- Keep event time separate from processing/ingestion time.
- Define how duplicate events are detected and handled.
- Use watermarks only when the business lateness bound is understood; a watermark does not guarantee retention of arbitrarily late events.
- Monitor consumer lag, input rate, processed rate, state-store size and failed batches.
- Design for at-least-once delivery and idempotent sink/change logic unless the entire source-to-sink path guarantees stronger semantics.
- Plan schema evolution deliberately; route malformed or unexpected records to an inspectable location.

### Choosing a processing mode

| Workload | Preferred pattern | Reason |
|---|---|---|
| Initial historical load | ADF batch + Databricks batch | Efficient bulk processing and reconciliation |
| Daily reference refresh | Scheduled ADF + incremental/full reference load | Predictable refresh cadence |
| New ride booking | Event Hubs + Structured Streaming | Low-latency event processing |
| Historical correction/backfill | Controlled batch replay | Reprocess a bounded range |
| Curated fact/dimension refresh | Declarative pipeline or orchestrated Spark job | Dependency-aware, repeatable transformation |

## 9. CDC and SCD Type 1 / Type 2

**CDC (Change Data Capture)** describes how inserts, updates and deletes are identified and delivered from a source. **SCD (Slowly Changing Dimension)** describes how a dimensional model stores changes to descriptive attributes. They are related but not interchangeable.

### CDC event contract

A source with CDC capability may provide:

| Field | Purpose |
|---|---|
| Business key | Identifies the entity being changed |
| Operation | Insert, update or delete |
| Sequence/version | Orders changes for the same key |
| Event/commit timestamp | Supports latency tracking and time analysis |
| Payload | New values or changed columns |

When the source has no reliable change feed, compare snapshots or use a well-defined watermark/change-detection strategy. A timestamp watermark is reliable only if source updates always advance it and late updates are handled.

### SCD Type 1 — latest state only

- Insert a new business key.
- Update the existing row when attributes change.
- Do not retain previous attribute values in the dimension.
- Use it when historical changes do not affect reporting, such as a corrected descriptive label.

**Example:** Driver D42's display name changes. The current row is updated; the previous name is not retained in the dimension.

### SCD Type 2 — preserve historical versions

- Expire the previously active row when a tracked attribute changes.
- Insert a new row with a new surrogate key.
- Store validity metadata such as effective start/end and current flag, or equivalent framework-managed fields.
- Resolve fact foreign keys to the dimension version valid at the ride's event time.

**Illustrative example:**

| driver_key | driver_id | driver_status | effective_start | effective_end | is_current |
|---:|---|---|---|---|---|
| 101 | D42 | Active | 2026-01-01 | 2026-04-14 | false |
| 208 | D42 | Inactive | 2026-04-15 | null | true |

Dates are illustrative. A ride on 2026-03-20 should resolve to key 101; a ride on 2026-05-02 should resolve to key 208.

### How to choose

| Requirement | Type 1 | Type 2 |
|---|---|---|
| Keep only current value | Yes | No |
| Report historical attribute state | No | Yes |
| Storage and join complexity | Lower | Higher |
| Surrogate key per historical version | Usually unnecessary for history | Yes, in a conventional Type 2 model |
| Example | Corrected payment label | Driver/location history where past-state reporting matters |

In Databricks declarative pipelines, CDC APIs and supported SCD modes depend on the runtime/product and API in use. Verify platform support before selecting AUTO CDC or an equivalent change-application API; do not assume every Spark Declarative Pipelines implementation exposes identical syntax.

## 10. Transformation examples

### A. Standardise and validate rides

~~~python
from pyspark.sql import functions as F

clean_rides = (
    rides_df
    .withColumn("ride_id", F.trim(F.col("ride_id").cast("string")))
    .withColumn("ride_timestamp", F.to_timestamp("ride_timestamp"))
    .withColumn("fare_amount", F.col("fare_amount").cast("decimal(12,2)"))
    .filter(F.col("ride_id").isNotNull())
    .filter(F.col("ride_timestamp").isNotNull())
)
~~~

In a complete implementation, invalid records should be counted and quarantined with a reason code rather than silently disappearing. Use actual source column names and types.

### B. Enrich with mappings

~~~python
enriched_rides = (
    clean_rides
    .join(payment_map, on="payment_method_id", how="left")
    .join(ride_type_map, on="ride_type_id", how="left")
    .join(vehicle_type_map, on="vehicle_type_id", how="left")
)
~~~

Before joining, verify mapping keys are unique; duplicate mapping keys can multiply ride rows and inflate measures. Measure unmatched codes explicitly. A left join preserves the ride record, but unmatched mapping fields still need a defined policy.

### C. CDC merge concept

~~~sql
MERGE INTO target AS t
USING source_changes AS s
ON t.business_key = s.business_key
WHEN MATCHED AND s.operation = 'DELETE' THEN DELETE
WHEN MATCHED AND s.operation IN ('UPDATE', 'INSERT')
  THEN UPDATE SET *
WHEN NOT MATCHED AND s.operation <> 'DELETE'
  THEN INSERT *;
~~~

This is a conceptual template. Production CDC needs deterministic sequencing, duplicate handling, explicit column mappings, a null/partial-update policy and a defined delete strategy. Validate syntax and semantics for the actual target/runtime.

### D. Fact integrity

Before publishing fact, validate:

- The selected grain is unique (for example, one row per ride_id if agreed).
- Required measures have valid types and business ranges.
- Each foreign key resolves to a dimension row or a documented unknown member.
- Type 2 dimension joins use the correct effective date interval.
- Source, Silver OBT and fact counts reconcile with explained exclusions.

## 11. Quality, reliability and recovery

| Failure / risk | Detection | Response |
|---|---|---|
| Invalid JSON or schema drift | Parse failures, rescued fields, schema checks | Quarantine payload, review contract, evolve schema deliberately |
| Duplicate ride/event | Duplicate-key counts and event IDs | Deterministic deduplication or idempotent merge |
| Late/out-of-order event | Event-time lag and sequence checks | Apply documented watermark/sequence policy; replay when needed |
| Missing mapping key | Unmatched mapping rate | Preserve record with unknown mapping and alert on threshold |
| Duplicate mapping key | Uniqueness assertion before join | Correct mapping source; prevent join fan-out |
| ADF activity failure | Pipeline status and activity output | Retry transient errors, fix access/configuration, rerun safely |
| Streaming restart | Query state and checkpoint health | Resume from valid checkpoint; do not share a checkpoint across unrelated queries |
| Incorrect SCD history | Multiple current rows or overlapping validity windows | Reconcile affected keys and repair history |
| Partial Gold refresh | Target freshness and row-count checks | Publish only after validation; use a controlled refresh strategy |
| Cost/latency regression | Runtime, backlog, input rate and compute metrics | Tune partitions, joins, trigger cadence and compute size |

**Operational principle:** a successful job status does not prove data correctness. Publish only after schema, freshness, counts, uniqueness and referential-integrity checks pass.

## 12. Development and production

### Development

- Use a dedicated development catalog/schema and storage paths.
- Use a small representative sample and synthetic events for rapid iteration.
- Keep secrets in approved secret management, not notebook cells or Git.
- Test transformations independently before running the full pipeline.
- Make checkpoints and output locations environment-specific.
- Test duplicate events, late arrivals, null keys, unknown mappings, schema changes and deletes.
- Use full refreshes only when a rebuild is intentional.

### Production

- Separate production identities, permissions, catalogs and storage locations from development.
- Use service principals or managed identities with least-privilege access where supported.
- Parameterise environment settings; avoid hard-coded workspace IDs and paths.
- Deploy notebooks and pipeline definitions through version control and an approved CI/CD workflow.
- Configure schedules, concurrency limits, retries, timeouts and alert routing.
- Keep streaming checkpoints durable and isolated per query.
- Apply quality gates before exposing new Gold outputs to consumers.
- Define replay, backfill, retention, recovery-time and recovery-point expectations.
- Monitor freshness, streaming lag, rejected records, cost and SLA compliance.
- Test deployment and rollback in a non-production environment first.

### Scenario: a ride event arrives twice

1. The same event ID is observed after a producer retry.
2. Bronze may retain both deliveries for traceability, depending on the raw-data policy.
3. Silver deduplicates using event ID or a stable business key plus sequence.
4. CDC/merge logic applies the change once logically.
5. A duplicate metric records the event; the fact grain remains unique.

### Scenario: a driver attribute changes

1. An updated driver record enters the change feed or is detected by snapshot comparison.
2. The change is ordered using a reliable source sequence/version.
3. Type 1 overwrites the active attribute if only current state is needed; Type 2 expires the old version and inserts a new one if history matters.
4. Fact-key resolution uses the dimension version appropriate for the ride event time.
5. Validation checks one active row per business key and no overlapping validity intervals.

### Scenario: a new source column appears

1. Detect the field and assess backward compatibility.
2. Preserve or quarantine the unexpected value rather than silently dropping it.
3. Update the source contract and transformation/schema configuration.
4. Validate downstream views and Gold schema in development.
5. Deploy through the release process and monitor the first production run.

## 13. Security and governance

- **Identity:** prefer managed identity/service principal authentication over embedded credentials.
- **Secrets:** store credentials in Azure Key Vault or approved secret scopes; never commit them.
- **Network:** restrict storage, Event Hubs and workspace access according to organisational policy.
- **Unity Catalog:** where enabled, use catalogs, schemas, grants and lineage to govern access.
- **Data minimisation:** expose only passenger/driver attributes needed for the use case.
- **Auditability:** preserve source/run metadata and log who or what triggered a load.
- **Retention:** define separate retention rules for raw payloads, curated tables and checkpoints.
- **Monitoring:** centralise ADF activity outcomes, Databricks job/pipeline status, stream metrics and quality results.

## 14. Setup checklist

Exact setup depends on the resources and code present in the repository. Use this checklist to configure or verify the environment:

1. **Azure resources:** subscription, ADLS Gen2, ADF, Databricks workspace and Event Hubs namespace/entity for streaming.
2. **Access:** configure identities and least-privilege permissions for ADF, Databricks, storage and Event Hubs.
3. **Storage layout:** agree on environment-specific Bronze/Silver/Gold paths or catalog/schema names.
4. **Batch ingestion:** configure ADF linked services, datasets, parameters, source locations and sink paths.
5. **Event producer:** configure the booking-event producer and Event Hubs connection through secure settings.

10. **Operations:** configure alerts, logging, run metadata, retention, replay and cost controls before unattended runs.

Never publish connection strings, SAS keys, access tokens, client secrets, storage keys or real passenger information.

## 15. Analytics use cases

Once the fact and dimension model is populated and validated, it can support questions such as:

- How many rides were requested or completed by day, hour or status?
- What is the total and average fare by payment method?
- Which vehicle types or makes are associated with the highest ride volume?
- How does demand vary by pickup/drop-off location?
- What percentage of bookings are cancelled, and what are the leading cancellation reasons?
- How do ride duration and distance vary across time periods?
- How did a driver's or location's descriptive state change over time where Type 2 history is retained?
- How fresh is the analytics dataset, and how many records were rejected or delayed?

Actual KPIs depend on the fields present and validated in the source schema.

| ADLS Gen2 | Azure Data Lake Storage Gen2 |
| Event Hubs | Azure event-ingestion service for high-throughput event streams |
| Structured Streaming | Spark engine for incremental stream processing |
| Delta Lake | Table/storage layer supporting transactional operations and versioning |
| Bronze / Silver / Gold | Raw, cleaned/enriched and curated data layers |
| OBT | One Big Table; a wide enriched dataset used as a transformation boundary |
| CDC | Change Data Capture; insert/update/delete changes from a source |

| SCD Type 2 | Retain historical versions of dimension attributes |
| SDP | Spark Declarative Pipelines; a declarative pipeline programming model |
| DLT | Delta Live Tables, the earlier Databricks name for its managed declarative pipeline product; terminology and APIs vary by platform/version |
| Fact grain | Exact business event represented by one row in a fact table |
| Watermark | Event-time boundary used to manage late data in streaming |
| Checkpoint | Durable stream progress/state used to recover a streaming query |
